> - **What the two runs share:** the data window, 2026-08-16 → 2026-09-15. They share no parameter value.

## 2. KQL for every tile, with the output it returned

How the queries reference the dashboard parameters:
- **The parameters are not declared in the queries.** They use `_startTime`, `_endTime` and `_facility_id`
  as the dashboard injects them.
- **To run a query outside the dashboard**, the test harness prepended:
  - `let _startTime = datetime(2026-08-16); let _endTime = datetime(2026-09-15);`
  - `let _facility_id = '<id>';`, for Facility Operations queries only.
- **The harness also rejected any query text containing** `now(`, `ago(`, `dcount(` or `| count`.

The horizon literal `datetime(2026-09-15)` is H_ent's exclusive end (`TOPOLOGY_AS_OF`,
01_topology_config:343). It is the only date literal in the tile queries. The release gate G1 also uses the
window's literal start, 2026-08-16.

### Executive Overview

#### T01 Source freshness

```kql
// T01 Source freshness · spec "Also settle: Freshness" + R1d · as-of: each source's own max; board end = window end capped at H_ent (last day 2026-09-14)
let W_start = startofday(_startTime);
let W_end   = min_of(startofday(_endTime), datetime(2026-09-15));   // H_ent exclusive end (R1b)
let board   = strcat("[", format_datetime(W_start, "yyyy-MM-dd"), ", ", format_datetime(W_end, "yyyy-MM-dd"), ")");
let cat = external_table('gold_plume_catalog');
union
 (cat | summarize t0 = min(detection_date), t1 = max(detection_date), n = count(),
                  h0 = min(detection_date - startofday(detection_date)), h1 = max(detection_date - startofday(detection_date)),
                  after = countif(detection_date >= W_end)
      | project ord = 1, source = "TROPOMI CH4 plumes (gold_plume_catalog.detection_date)", estate = "real",
                as_of_utc = format_datetime(t1, "yyyy-MM-dd HH:mm:ss"),
```

```kql
// E4 is the median across plumes (the catalog's spread, not any plume's uncertainty); E5 shows that plume's own band.
// fmt(v, dp): the exact value as text with thousands separators, so the card never abbreviates (no "5.1M").
// The precision must be a literal at each call.

    let r  = round(v, dp);
    let s  = tostring(r);
    let ip = tostring(split(s, ".")[0]);
    let fp = iff(array_length(split(s, ".")) > 1, tostring(split(s, ".")[1]), "");
    let L  = strlen(ip);
    let g  = case(L > 9, strcat(substring(ip, 0, L - 9), ",", substring(ip, L - 9, 3), ",", substring(ip, L - 6, 3), ",", substring(ip, L - 3, 3)),
                  L > 6, strcat(substring(ip, 0, L - 6), ",", substring(ip, L - 6, 3), ",", substring(ip, L - 3, 3)),
                  L > 3, strcat(substring(ip, 0, L - 3), ",", substring(ip, L - 3, 3)),
                  ip);
    iff(dp <= 0, g, strcat(g, ".", substring(strcat(fp, "0000000000"), 0, dp)))
};
```

**Why two tables.** Drill-through is configured per visual: Edit visual > Interactions > drillthrough, with
a column-to-parameter pair and a destination page.
- **No per-row condition is documented**
  (learn.microsoft.com/fabric/real-time-intelligence/dashboard-interactions). What a null cell does on
  click is not documented either.
- **The split makes the rule structural.** T11a, the attributed plumes, has drill-through on, from
  `facility_id` to `_facility_id`, landing on Facility Operations. T11b, the 7 unattributed plumes, has it
  off.
- **T11b shows `source_lat/lon` instead of a facility.**

Decision B in the output:
- **No single-candidate plume shows a number.** The 6 single-candidate plumes in the window read
  "only candidate within 50 km". The 7th is outside the window.
- **High shares never show as 1.00.** Multi-candidate shares of 0.995 or more read "> 0.99 share of n
  candidates". Two do: PL-e7c7f1b2ad9d and PL-fba050bced02.
- **`attribution_method`** shows `wind_aware` 41, `distance_only` 1 and `no_match` 7.
- **The `distance_only` plume is PL-8a46231dbd67.** It is the fixed-48 h fallback plume, 0.4 t/h,

## 5. Freshness tile

T01 (§2) is the freshness tile, and it sits on both pages.

**What it answers from the data:**
- **The as-of of each of the four sources.**
- **TROPOMI overpass window:** 19:35–20:35 UTC, read from `detection_date`, which is the first pixel row's
  time.
- **How many plumes carry ERA5 wind:** 50 of 50. One fell back to the fixed 48 h mixing time.
- **That the detection horizon runs one day past the board,** and why.

**What it cannot answer, and says so:**
- **ERA5 latency and the extract's identity.** 02b loads a manually downloaded ERA5 extract that must cover
  the run window (02b:142–180). 03 joins it per pixel at the nearest hour and the nearest grid point
  (03_join_data:421–453). The extract's file name, download date and ERA5/ERA5T status are not written to
  any serving table.
- **NRTI vs OFFL per plume.** 02 ingests both (02_ingest_tropomi_ch4:47, 170), but `stac_id` in the catalog
  does not carry the processing mode. A regex for `S5P_(OFFL|NRTI)_` matched 0 of 50.
- **A run timestamp.** The catalog has no run timestamp column, and 04/05 overwrite the whole table.

```markdown
# Green Sky — RTI board V2: how to read it

## What is real and what is not
- REAL: the satellite side of every plume — when it was seen, where its source pixel is, the methane in it
  (IME), its emission rate and that rate's P5–P95 band, the ERA5 wind used.
- SYNTHETIC: everything with a facility in it — the 150 facilities (topology_seed 20260915), which facility a
  plume is attributed to, work orders, maintenance, LDAR, sensors, alarms, SCADA. The banner at the top of each
  page says so, and the estate column in the tables marks which rows are real and which are synthetic.
- Facility names are decorative: the town in a name is drawn independently of the coordinates. Read the
  facility_id, never the name, and never read a name as a place.

## Dates
- Satellite detections run to 2026-09-15; the synthetic enterprise and SCADA data run to 2026-09-14.
  Every tile on this board stops at 2026-09-14 so that the two never disagree. One plume (2026-09-15) is
  therefore not shown; the freshness strip counts it.
- The window selector defaults to 2026-08-16 → 2026-09-15 (end exclusive). Pick any part of it. Ranges past
  2026-09-15 are capped. The freshness strip at the top of each page prints the date the page is "as of";
  a tile with a different date (the consistency check, facility identity) prints its own.
- "As of end of <day>" figures (open work orders, overdue maintenance, leaks outstanding, standing alarms,
  risk points) are the state at midnight UTC ending that day. They are never added across days.
- There is no "now". The pipelines are not scheduled; nothing on this board is live.

## Reading the tiles
- Titles are short on purpose. They do not repeat "synthetic": the banner at the top of each page and the
  estate column in the tables mark what is real and what is synthetic.
- Detected plumes, Unattributed plumes, Plumes at this facility: one row per plume, sorted by point rate,
  each with that plume's own P5-P95 band. A facility_id in the detected-plumes table opens that facility's
  page; unattributed plumes have no facility to open.
- Observed plume methane, Daily observed methane, Facilities by observed methane: point estimates in t CH4.
  The ranking's last two rows are the unattributed bucket and the catalog total; facilities plus
  unattributed equal the total.
- Emission rate by plume: three points per plume (point estimate, P5, P95), ranked by point rate. The
  horizontal line is the 25 t/h ultra-emitter threshold of Lauvaux et al. 2022, for reference only.
- Risk points by component, Risk points by day: the five components are stacked for reading. They are
  never added up into a score.
- Each page has a headline (a few large numbers to read first) and, below it, a compact table with the
  rest. On the executive page that table holds the splits and the reconciliation (facilities plus
  unattributed equal the catalog total). On the facility page it holds operations and compliance, which
  are zero for most facilities.
- A headline card that says "none in window" means there is nothing to count, not a measured zero.
- Work orders, maintenance, leaks, sensors, alarms and open cases are the state at midnight UTC ending the
  as-of day.
- Financial impact ("est." on the facility page) is a point estimate in USD for attributed plumes only,
  social cost off. The lost-gas and fines rows are derived from the total.

- "Observed plume methane" (t CH4) is the methane in the plume at the moment of the overpass (the IME). It is
  a floor on what was released, not an emission total, and not a daily or annual figure.
- Emission rate (t/h) is a point estimate for one overpass, with the 5th–95th percentile of 500 Monte Carlo
  draws for that plume. Totals are sums of point estimates; no total carries a band.
- No severity tiers. The board sorts by rate. The one line on the distribution chart is the 25 t/h
  "ultra-emitter" threshold of Lauvaux et al. 2022, for reference only. The catalog's median rate (~19.7 t/h)
  sits close to that line, and detection density here runs well above independent inventories while known
  striping artefacts are unresolved, so a high rate is a lead to check, not a confirmed super-emitter.
- "confidence" on a plume (high / medium) is a points grade from wind alignment, uncertainty ratio and pixel
  count. It is not a probability.
- TROPOMI passes over the basin once a day, early afternoon local time (19:35–20:35 UTC in this window). A
  plume is a snapshot at that instant; the board never turns a rate into a daily mass.

- Each plume is matched to the synthetic facilities within 50 km, weighted by distance and by how well the

  probability that the facility is the source.
- "only candidate within 50 km" means exactly one facility was in range; its share is 1 by construction and is
  not shown as a number.
- attribution_method: wind_aware (ERA5 wind used), distance_only (wind below 0.5 m/s, distance alone),

  and in their own detection table; clicking a facility in the attributed table opens its page.

- Facilities are ranked on observed plume methane in the window, then on plume count. There is no single
```

## 11. Proposal: make the detection → enterprise dependency loud

**The failure mode.** `greensky_detection` (04, 05) overwrites `gold_plume_catalog`. Nothing obliges
`greensky_enterprise` to follow.
- **Why it happens.** 03c and 03e read the catalog only when they run.
- **The effect.** If detection is re-run alone, the board reads a snapshot built on the previous
  attribution, beside a catalog with the new one.
- **This has already happened.** It was the state of things on 2026-10-15.

**Why the suggested guard in 03e would not catch it.**
- **03e doesn't run in the failure case.** "Fail 03e when `gold_plume_catalog` is newer than the snapshot"
  only fires when 03e runs. In the failure case, enterprise is not run at all.
- **It would also block the fix.** When enterprise *is* run, the catalog is newer than the old snapshot
  by definition. The guard would fail the very run that repairs the state.
- **A guard has to sit where the two meet** (the board), or where the catalog changes (the end of
  detection).

**Proposed, in order of value. None is implemented.**

1. **A consumer-side gate on the board.** Read-only, with no pipeline change and no fifth table.
   - **What it is.** Put G1 (§7) on both pages as a "Data consistency" tile, beside freshness.
   - **When it fails.** When G1 returns any status other than `match`, the tile shows "ENTERPRISE DATA
     PREDATES CURRENT ATTRIBUTION: n facility-days differ".
   - **Self-gating tiles.** Every tile that reads attribution-derived snapshot columns embeds the same
     test. While it fails, the tile returns one row, "withheld: snapshot predates attribution", instead of
     numbers. This covers E6, E7, E9, the two risk components, and once §0.2's correction is accepted, the
     ticket and maintenance stocks.
   - **Why first.** It catches every route to the mixed state: the pipeline, a manual notebook run, or a
     partial re-run. It fails at the point where a reader would be misled. It is content-based, not
     time-based, so an 04 re-run that changes nothing does not raise it.
   - **Limit.** It sees plume-column mismatch, the direct signature of this failure. A 03c re-run without
     03e would not show in G1; item 2 covers that.
2. **Producer-side lineage.** Small notebook changes.
   - **Fingerprint.** 05 computes a catalog fingerprint at the end of its run: SHA-256 over the sorted
     `plume_id | attributed_facility_id | ime_kg`.
   - **Where it is recorded.** 05, 03c and 03e each write the fingerprint they consumed or produced to a
     run-log table (for example `meta_run_lineage`, with run id, notebook, window, catalog Delta version,
     fingerprint and timestamp).
   - **Not as a snapshot column.** That would be a served-schema change, which means a shortcut rebuilt by
     hand (spec R6c).
   - **The 03e assertion.** 03e asserts that the fingerprint 03c recorded equals the one it now reads. This
     catches detection running between 03c and 03e, and a stale 03c.
   - **Making it visible on the board.** It needs the run-log table served, which is a fifth-table
     decision.
3. **Structural: chain the pipelines.** This removes the failure rather than reporting it.
   - **The change.** `greensky_detection` ends with an Invoke Pipeline activity on success, running
     `greensky_enterprise` with `run_mode=backfill` and `pipeline_date` empty. An umbrella pipeline would
     do the same.
   - **Why backfill.** Enterprise cannot run incrementally until the date refactor lands
     (`DESIGN_NOTE_date_refactor.md` §4).
   - **The cost.** About 41 minutes on every detection re-run.
   - **Why it's acceptable.** The generators are hash-seeded and deterministic. Only the
     attribution-driven parts change: 03c cases, the tickets raised from them, and 03e.

**Status (third pass).** Option 1 is built: B1, T12, and the gating in T08, T10, T23 and T25. Options 2 and
3 are open items (§9).

**Recommendation.**
- **Do 1 now.** It is board work, and G1 already exists and runs.
- **Do 3 when the pipelines are next edited.**
- **Treat 2 as hardening.** It is worth doing alongside the provenance columns in §9 item 2, since both
  change what 04/05 write.
